# AGENTS.md — Asoti Food Shop

Краткие рабочие правила для ИИ-агентов и разработчиков. Документ должен
описывать текущее состояние репозитория; обновляйте его вместе с изменениями
архитектуры, запуска, деплоя и подтверждённых бизнес-правил.

## Источник правды

При расхождении ориентируйтесь в таком порядке:

1. исполняемый код, настройки и миграции;
2. тесты;
3. `pyproject.toml`, env-примеры и Docker Compose;
4. этот файл.

`truth_parts/` содержит исторические материалы и планы, а не реализованное
поведение. Не принимайте их за спецификацию без проверки кода.

## Проект и границы MVP

Asoti Food Shop — серверный интернет-магазин на Django для `asotia.ru`.

В MVP входят:

- каталог, категории, карточки товаров и поиск;
- session-based корзина с проверкой остатков;
- гостевой checkout и заказы авторизованных пользователей;
- регистрация, вход по email, профиль и история заказов;
- управление через Django admin;
- email/Telegram-уведомления о заказах;
- информационные страницы.

Без отдельной задачи не добавляйте онлайн-оплату, интеграции служб доставки,
DRF, Celery, SPA-фронтенд, отдельную админ-панель или сложную программу
лояльности.

## Стек и структура

- Python `^3.12`, Django `^5.2`;
- PostgreSQL 15;
- Redis 7 подготовлен контейнером, но приложением пока не используется;
- Poetry, pytest + pytest-django, Ruff;
- Gunicorn + systemd в production.

Точные версии находятся в `pyproject.toml` и `poetry.lock`. Не обновляйте
зависимости без необходимости и не редактируйте lock-файл вручную.

```text
apps/
  accounts/   авторизация, профиль, кабинет
  catalog/    категории и товары
  cart/       session-based корзина
  orders/     checkout, заказы, уведомления
  pages/      главная и информационные страницы
  core/       только действительно общие компоненты
config/
  settings/   base.py, dev.py, prod.py
  urls.py
templates/    Django-шаблоны
static/       исходные статические файлы
media/        пользовательские загрузки; не коммитятся
locale/       переводы
```

Каждое приложение владеет своей предметной областью. Не переносите логику в
`core` только ради абстракции.

## Локальная разработка

Команды выполняются из каталога с `manage.py`:

```powershell
poetry install
Copy-Item .env.example .env
docker compose up -d
poetry run python manage.py migrate
poetry run python manage.py runserver
```

Локальные endpoints:

- сайт: `http://127.0.0.1:8000/`;
- admin: `http://127.0.0.1:8000/admin/`;
- debug toolbar: `http://127.0.0.1:8000/__debug__/`;
- PostgreSQL: `127.0.0.1:5433`;
- Redis: `127.0.0.1:6379`.

`docker-compose.yml` и dev-настройки используют PostgreSQL `5433:5432`.
Останавливайте сервисы через `docker compose down`. Не используйте `down -v`,
если пользователь явно не попросил удалить локальные данные.

Запускайте только один `runserver`. Если порт 8000 отдаёт старый код, сначала
найдите владельца порта и проверьте всю родительскую цепочку процесса:

```powershell
Get-NetTCPConnection -LocalPort 8000 -State Listen
Get-CimInstance Win32_Process -Filter "ProcessId = <PID>"
```

Завершайте процесс только после проверки `CommandLine`; не останавливайте
чужие Python/Poetry-процессы.

## Настройки и секреты

- `manage.py` по умолчанию использует `config.settings.dev`;
- production использует `config.settings.prod`;
- настройки читаются из корневого `.env` через `django-environ`;
- `.env` и `.env_prod` не коммитятся;
- `.env.example` и `.env.prod.example` содержат только безопасные примеры;
- при добавлении обязательной переменной обновляйте соответствующий пример;
- никогда не выводите, не копируйте и не коммитьте реальные секреты.

## Архитектурные правила

### URL, views и шаблоны

- Сохраняйте `app_name` и именованные URL.
- Маршруты приложения объявляйте в его `urls.py`, подключение — в
  `config/urls.py` через `include()`.
- Публичные URL и имена маршрутов не меняйте без необходимости.
- Views координируют запрос и ответ; объёмную бизнес-логику выносите из views.
- Пользовательские страницы собирайте Django-шаблонами, не HTML-строками.

### Каталог и слаги

- `Category.slug` и `Product.slug` поддерживают кириллицу через
  `SlugField(..., allow_unicode=True)`; не возвращайте ASCII-only валидацию.
- Категории каталога плоские. Вид продукции, состав, основной ингредиент,
  упаковка и особенности задаются через `Attribute`/`AttributeValue`, а не
  через вложенные категории или фиксированные `TextChoices`.
- Каталожные URL используют `<str:...>`, чтобы принимать Unicode-слаги.
- Слаг товара уникален внутри категории (`category`, `slug`).
- Товар связывается со значениями через `ProductAttributeValue`; одна связь не
  может дублироваться. Одному товару можно назначить несколько значений одной
  характеристики.
- `ProductQuerySet.filter_by_attribute_values()` объединяет значения одной
  характеристики через OR, а разные характеристики — через AND. Публичные
  запросы начинайте с `Product.objects.public()`.
- Подборки задаются моделями `Collection` и `CollectionRule`. Категории внутри
  подборки объединяются через OR; отсутствие категорий означает весь каталог.
- Наличие определяется только по `stock_quantity`: при нуле товар нельзя
  добавить в корзину. Признак «Без мяса» назначается только явно.
- Django admin заполняет слаг из названия через `prepopulated_fields`.
- Любое изменение правил слага сопровождайте миграцией и тестом model/form
  validation, а не только созданием объекта через ORM.

### Корзина и заказы

- Корзина хранится в Django session и ограничивает количество остатком товара.
- Гостевой checkout остаётся обязательным сценарием.
- Имя и телефон обязательны; email и адрес необязательны. Пустой адрес
  сохраняется пустой строкой и не блокирует заказ.
- Для авторизованного пользователя имя берётся из `User.first_name`, телефон и
  адрес — из `accounts.Profile`. Новые значения сохраняются в профиль только
  после успешного оформления.
- Фамилия в пользовательском интерфейсе не используется.
- Заказ хранит снимки данных и цены товарных позиций.
- Создание заказа, позиций и уменьшение остатков выполняются атомарно; корзина
  очищается только после успешного сохранения.
- Заказ авторизованного пользователя связан с `AUTH_USER_MODEL` и отображается
  в кабинете; регистрация для checkout не обязательна.
- Уведомления запускаются после commit. Ошибка email/Telegram не должна
  откатывать заказ; пустая конфигурация отключает канал.
- Денежные значения храните в `DecimalField`, не `FloatField`.

### UI и CSS

- Интерфейс mobile-first на Django templates, без frontend-фреймворка.
- Общая оболочка находится в `templates/base.html`, основные стили — в
  `static/css/site.css`.
- Используйте scoped-классы; избегайте широких селекторов, затрагивающих
  вложенные компоненты.
- Товарные изображения отображаются в квадратных контейнерах: каталог и
  корзина используют центрированный `object-fit: cover`, карточка товара —
  центрированный `object-fit: contain` на тёмном фоне. Исходные файлы в
  `media/` для этого не обрезаются и не перезаписываются.
- Миниатюры корзины имеют размер `96 × 96 px` на desktop и `72 × 72 px` на
  mobile; каталожная сетка сохраняет четыре колонки на desktop и две на mobile.
- POST-формы должны иметь CSRF-защиту.
- При UI-изменениях проверяйте примерно `390px` и `1280px`, горизонтальное
  переполнение, изображения и фиксированную мобильную навигацию.

## Правила изменений

- Перед правкой изучите затронутые модели, формы, URL, настройки и тесты.
- Делайте минимальное изменение, решающее задачу.
- Не переписывайте чужие незавершённые изменения и несвязанные файлы.
- Изменение модели всегда сопровождается миграцией в том же наборе изменений.
- Не редактируйте и не удаляйте пользовательские файлы в `media/`.
- Не коммитьте env-файлы, логи, кэши, локальные БД и IDE-настройки.
- Не выполняйте destructive-команды для Git, Docker или БД без явного запроса.
- Повторяемую предметную логику выносите после появления реального повторения;
  не создавайте абстракции заранее.

Код и тексты:

- Python/Django-код следует текущему стилю проекта;
- Ruff: Python 3.12, длина строки 88;
- type hints добавляются там, где улучшают контракт;
- UI и тексты сайта — на русском, идентификаторы и файлы — на английском;
- текстовые файлы — UTF-8; mojibake недопустим.

## Проверки

Выбирайте проверки пропорционально изменению:

| Изменение | Обязательные проверки |
| --- | --- |
| Python/Django | `poetry run ruff check .`, `poetry run python manage.py check` |
| Поведение приложения | целевые pytest-тесты изменённого приложения |
| Модели | целевые тесты + `makemigrations --check --dry-run` |
| Несколько приложений/общий поток | полный `poetry run pytest` |
| Production-настройки | `manage.py check --deploy` с корректным production env |

Полезные команды:

```powershell
poetry run ruff format .
poetry run ruff check .
poetry run python manage.py check
poetry run pytest apps/catalog/tests.py -q
poetry run python manage.py makemigrations --check --dry-run
```

`ruff check --fix` и форматирование всего репозитория запускайте только после
оценки масштаба diff. Если проверка заблокирована внешней инфраструктурой,
зафиксируйте точную причину вместо заявления об успешном прохождении.

Импорт актуального каталога из UTF-8-снимка старой схемы:

```powershell
poetry run python -X utf8 manage.py import_catalog_snapshot `
  backups/catalog-refactor-2026-09-11/catalog-before-utf8.json `
  --report catalog_manual_review.md
```

Команда повторяемая и читает только экспорт актуальных `catalog_category` и
`catalog_product`. Она сохраняет ID товаров, цены, остатки, активность и пути к
изображениям, не скачивает и не изменяет `media/`. Legacy-таблицы `categories`
и `products` в новой базе не создаются.

История миграций `catalog` и `orders` очищена до новых `0001_initial`. Старую
базу с уже применёнными дорефакторинговыми миграциями нельзя обновлять поверх:
сначала сделайте и проверьте резервную копию, затем пересоздайте только целевую
БД и импортируйте снимок каталога. Встроенные миграции Django не изменялись.

## Production и деплой

Стандартный `deploy.sh`:

- работает из корня с `.git`, `manage.py` и закрытым `.env`;
- требует чистое рабочее дерево и выполняет только fast-forward;
- проверяет endpoint БД, запускает checks, миграции и `collectstatic`;
- перезапускает systemd-сервис и при настройке выполняет HTTP healthcheck.

```bash
APP_DIR=/var/www/asotia \
BRANCH=main \
SERVICE_NAME=asotia.gunicorn \
HEALTHCHECK_URL=https://asotia.ru/ \
./deploy.sh
```

Текущий production использует историческую обёртку:

```text
/home/o_adm/www/asotia/
  update.sh
  .env          закрытый файл, права 600
  .venv/
  app/          Git-репозиторий и Django-корень
    .env        ссылка на ../.env
```

- обновление: `cd /home/o_adm/www/asotia && ./update.sh`;
- ветка: `main`;
- SSH: порт `2230`;
- сервис: `asotia.gunicorn.service`;
- сокет: `/run/asotia/gunicorn.sock`.

Production-БД нового магазина — только PostgreSQL 15 из
`docker-compose.prod.yml`:

- контейнер `asotia_postgres15`;
- `127.0.0.1:15432` с хоста;
- volume `asotia_postgres15_data`;
- `DATABASE_URL` обязан указывать `127.0.0.1:15432`.

Не подключайте магазин к системным PostgreSQL на `5432` или `5433`: там
работают другие проекты. Production-настройки намеренно не имеют fallback для
`DATABASE_URL`, а `deploy.sh` проверяет host/port. Меняйте ожидаемый endpoint
только осознанно через `EXPECTED_DATABASE_HOST` и `EXPECTED_DATABASE_PORT`.
Никогда не используйте `docker compose down -v` на production.

Диагностика:

```bash
systemctl status asotia.gunicorn --no-pager -l
journalctl -u asotia.gunicorn -n 100 --no-pager
```

Не публикуйте содержимое production `.env` в логах, коммитах или сообщениях.

## Критерии готовности

Изменение готово, когда:

1. реализовано требуемое поведение без лишнего расширения scope;
2. diff не содержит несвязанных правок и секретов;
3. релевантные проверки прошли или документирован внешний блокер;
4. миграции добавлены и согласованы с моделями;
5. env-примеры и этот файл обновлены, если изменились настройки, запуск,
   архитектура или подтверждённые бизнес-правила.
