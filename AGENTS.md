# AGENTS.md — Asoti Food Shop

Рабочие правила для ИИ-агентов и разработчиков. Документ описывает текущее
состояние репозитория и обновляется вместе с архитектурой, запуском, деплоем и
подтверждёнными бизнес-правилами.

## Источник правды

При расхождении ориентируйтесь в таком порядке:

1. исполняемый код, настройки и миграции;
2. тесты;
3. `pyproject.toml`, env-примеры, Docker и deploy-файлы;
4. этот документ.

## Проект и MVP

Asoti Food Shop — серверный интернет-магазин на Django для `asotia.ru`.

Реализованы:

- каталог, вложенные категории, карточки товаров, фильтрация, сортировка и
  поиск;
- session-based корзина с ограничением количества остатком;
- гостевой checkout и заказы авторизованных пользователей;
- регистрация, вход по email, профиль и история заказов;
- управление через Django admin;
- email/Telegram-уведомления о новых заказах;
- главная и информационные страницы.

Без отдельной задачи не добавляйте онлайн-оплату, интеграции доставки, DRF,
Celery, SPA, отдельную админ-панель или программу лояльности.

## Стек и структура

- Python `^3.12`, Django `^5.2`;
- PostgreSQL 15;
- Poetry, pytest + pytest-django, Ruff;
- Pillow для изображений;
- Gunicorn + systemd в production.

```text
apps/
  accounts/   регистрация, email-вход, профиль, кабинет
  catalog/    категории, товары, каталог и legacy-импорт
  cart/       корзина в Django session
  orders/     checkout, заказы и уведомления
  pages/      главная и информационные страницы
config/
  settings/   base.py, dev.py, prod.py
templates/    Django-шаблоны
static/       исходные CSS и JS
media/        пользовательские файлы, не коммитятся
```

Каждое приложение владеет своей предметной областью. Не создавайте общий app
или service-слой ради абстракции без реального повторения логики.

## Локальный запуск

Команды выполняются из каталога с `manage.py`:

```powershell
poetry install
Copy-Item .env.example .env
docker compose up -d
poetry run python manage.py migrate
poetry run python manage.py runserver
```

Локально сайт и admin доступны на `127.0.0.1:8000`, PostgreSQL — на `5433`.
Dev-настройки добавляют debug toolbar по адресу `/__debug__/`.

Останавливайте контейнеры через `docker compose down`. Не используйте
`docker compose down -v` без явного запроса на удаление данных.

## Настройки и секреты

- `manage.py` по умолчанию использует `config.settings.dev`, production —
  `config.settings.prod`;
- настройки читаются из корневого `.env` через `django-environ`;
- `.env` не коммитится; `.env.example` и `.env.prod.example` содержат только
  безопасные примеры;
- при добавлении обязательной переменной обновляйте соответствующий пример;
- не выводите и не коммитьте реальные секреты;
- production требует `DATABASE_URL`, dev имеет fallback на PostgreSQL `5433`;
- пустая конфигурация email или Telegram отключает соответствующий канал.

## Фактические бизнес-правила

### Каталог

- `Category.slug` и `Product.slug` допускают Unicode; URL используют
  `<str:...>`.
- Слаг товара уникален внутри категории, слаг категории уникален глобально.
- Страница категории показывает выбранную категорию и её активных прямых
  потомков; рекурсивный обход глубже одного уровня не реализован.
- Покупка определяется через `Product.is_active` и `stock_quantity > 0`.
  `stock_status` автоматически синхронизируется при сохранении остатка;
  `on_order` сохраняется для товара с нулевым остатком.
- Денежные значения хранятся в `DecimalField`.

### Аккаунты

- Используется стандартный Django `User`, не custom user model.
- Регистрация принимает email и пароль, создаёт технический UUID в `username`
  и профиль. Вход выполняется по email через пользовательскую форму.
- Email уникален без учёта регистра: формы дают пользовательскую ошибку, а
  PostgreSQL дополнительно защищён функциональным unique index. Пустой email
  разрешён для записей, созданных вне пользовательской регистрации.
- Пользовательский интерфейс использует только `first_name`; фамилия не входит
  в формы профиля и checkout.

### Корзина и заказы

- Корзина хранит `{product_id: quantity}` в Django session, удаляет
  неактивные/недоступные товары и ограничивает количество текущим остатком.
- Изменения корзины выполняются только POST-запросами с CSRF-защитой.
- Гостевой checkout обязателен. Имя и телефон обязательны; email и адрес
  необязательны.
- Для авторизованного пользователя checkout подставляет `first_name`, email,
  телефон и адрес. После успешного заказа имя, телефон и адрес обновляются.
- Заказ хранит снимки названия, цены, количества и суммы позиций.
- Создание заказа, блокировка товаров, пересчёт цены и уменьшение остатков
  выполняются в одной транзакции. Корзина очищается после сохранения.
- Уведомления регистрируются через `transaction.on_commit`; ошибки каналов не
  откатывают заказ. Отправка выполняется синхронно в процессе web-запроса.

### Изображения

- При сохранении нового `Product.image` поддерживаемое Pillow изображение
  получает EXIF-ориентацию, уменьшается максимум до `1200x1200` с сохранением
  пропорций и пересохраняется как JPEG quality 82.
- Это поведение находится в `Product.save()` и действует для admin,
  legacy-импорта и других обычных сохранений модели.
- Новый JPEG сохраняется до удаления загруженного исходника; при замене старый
  файл товара удаляется после успешной обработки.
- Nginx должен пропустить исходный файл до Django; текущий рекомендуемый лимит
  загрузки — `20M`.

## URL, views и UI

- Сохраняйте `app_name`, именованные URL и текущие публичные пути.
- Маршруты объявляются в `apps/*/urls.py` и подключаются через
  `config/urls.py`.
- Views координируют запрос и ответ; транзакционная логика checkout находится
  в `apps/orders/services.py`.
- UI server-rendered и mobile-first. Общая оболочка — `templates/base.html`,
  стили — `static/css/site.css`, улучшение корзины через fetch —
  `static/js/site.js` с обычным POST fallback.
- Изображения товара квадратные: в списках `object-fit: cover`, в карточке
  товара `object-fit: contain` на тёмном фоне.
- Сетка главной/общего каталога: четыре колонки desktop и две mobile;
  category detail использует отдельный адаптивный список.
- При UI-изменениях проверяйте примерно `390px` и `1280px`, переполнение,
  изображения и фиксированную мобильную навигацию.

## Правила изменений

- Сначала изучите затронутые модели, формы, URL, настройки и тесты.
- Делайте минимальное изменение и не переписывайте несвязанные правки.
- Изменение схемы модели сопровождается миграцией в том же наборе изменений.
- Не редактируйте и не удаляйте пользовательские файлы в `media/`.
- Не коммитьте env-файлы, логи, кэши, локальные БД и IDE-настройки.
- Не выполняйте destructive-команды для Git, Docker или БД без явного запроса.
- Python следует текущему стилю; Ruff настроен на Python 3.12 и 88 символов.
- Тексты сайта — на русском, идентификаторы — на английском, файлы — UTF-8.

```powershell
poetry run ruff check .
poetry run python manage.py check
poetry run python manage.py makemigrations --check --dry-run
```

Для production-настроек запускайте `manage.py check --deploy` с безопасным
тестовым production env. Не запускайте массовый `ruff --fix` или форматирование
всего репозитория без оценки diff.

## Legacy-импорт

`python manage.py import_legacy_catalog [--dry-run] [--skip-images]` переносит
старые таблицы `categories`/`products`. Команда повторяемая и покрыта тестами,
но требует обе старые и новые схемы в одной БД. Не запускайте её на production
без отдельной проверки источника и резервной копии.

## Production и деплой

`deploy.sh` требует корень Git-репозитория с закрытым `.env`, ветку `main` и
чистое рабочее дерево, включая отсутствие untracked-файлов. Он делает только
fast-forward, устанавливает main dependencies, проверяет endpoint БД,
запускает deploy-check, миграции,
`collectstatic`, перезапускает systemd-сервис и опционально проверяет URL.

Текущий сервер использует обёртку и layout:

```text
/home/o_adm/www/asotia/
  update.sh
  .env          права 600
  .venv/
  app/          Git-репозиторий и Django-корень
    .env        ссылка на ../.env
```

- обновление: `cd /home/o_adm/www/asotia && ./update.sh`;
- SSH: порт `2230`;
- ветка: `main`;
- systemd: `asotia.gunicorn.service`;
- Gunicorn socket: `/run/asotia/gunicorn.sock`;
- production PostgreSQL: контейнер `asotia_postgres15`, host endpoint
  `127.0.0.1:15432`, volume `asotia_postgres15_data`.

`DATABASE_URL` production обязан указывать `127.0.0.1:15432`. Не используйте
системные PostgreSQL на `5432`/`5433` и никогда не выполняйте
`docker compose down -v` на production.

Для Nginx задавайте в основном HTTPS `server`-блоке с
`server_name asotia.ru`:

```nginx
client_max_body_size 20M;
```

После изменения: `sudo nginx -t` и `sudo systemctl reload nginx`.

Прямой запуск стандартного deploy-скрипта для текущего сервера:

```bash
APP_DIR=/home/o_adm/www/asotia/app \
BRANCH=main \
SERVICE_NAME=asotia.gunicorn \
HEALTHCHECK_URL=https://asotia.ru/ \
./deploy.sh
```

Не меняйте production endpoint, не раскрывайте `.env` и не трогайте
production-данные без явной задачи.
